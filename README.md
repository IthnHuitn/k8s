### Задание 1: Выбрать стратегию обновления приложения и описать ваш выбор

1. Имеется приложение, состоящее из нескольких реплик, которое требуется обновить.
2. Ресурсы, выделенные для приложения, ограничены, и нет возможности их увеличить.
3. Запас по ресурсам в менее загруженный момент времени составляет 20%.
4. Обновление мажорное, новые версии приложения не умеют работать со старыми.
5. Вам нужно объяснить свой выбор стратегии обновления приложения.

### Ответ

1. Выбранная стратегия: Recreate
2. Аргументация выбора

При выборе стратегии я руководствуюсь тремя ключевыми ограничениями:

   - Мажорное обновление (несовместимость версий).

   - Жесткий лимит ресурсов (CPU/RAM) с запасом всего 20%.

   - Невозможность увеличить ресурсы кластера.

Рассмотрим все доступные стратегии по порядку:
Почему Rolling Update (стандартная) — не подходит

   - Проблема с ресурсами: При Rolling Update новые поды создаются до того, 
   как старые будут полностью удалены (по умолчанию maxSurge: 25%). Это означает, 
   что в момент обновления одновременно работают и старые, и новые реплики. 
   Потребление ресурсов возрастает минимум на 25% (или на величину maxSurge). 
   У нас есть свободных только 20%. Это приведет к тому, что новые поды не смогут 
   запуститься из-за нехватки памяти или CPU (OOMKill или Pending).

   - Проблема с несовместимостью: Даже если мы настроим maxSurge: 0, старые поды 
   будут завершаться постепенно, а новые — вставать на их место. В течение некоторого 
   времени старые и новые версии будут сосуществовать в одном Service. Если новые 
   версии не умеют работать со старыми (например, изменилась схема БД или API), 
   то часть запросов от балансировщика упадет на новые поды, которые не поймут 
   данные от старых клиентов, или наоборот. Это вызовет ошибки 500 для пользователей 
   во время обновления.

Почему Blue-Green или Canary (кастомные) — не подходят

   - Эти стратегии подразумевают развертывание новой версии параллельно со старой 
   (создание второго набора подов). Это требует удвоения ресурсов 
   (или как минимум +100% к текущему потреблению). При наличии свободных 20% 
   это физически невозможно реализовать в рамках одного кластера/ноды.

Почему Recreate — идеальный выбор

Эта стратегия работает по принципу:

   - Убить все старые поды сразу.

   - Дождаться их полного завершения.

   - Запустить все новые поды.

Почему это решает проблемы:

   - Ресурсы (экономия): Мы полностью освобождаем ресурсы, занятые старыми подами, 
   и только после этого запрашиваем ресурсы для новых. В момент запуска новых подов 
   старых уже нет. Пиковое потребление ресурсов не превышает обычное (100% от лимита), 
   а у нас есть запас в 20%, чтобы новые поды успешно прошли инициализацию и старт.

   - Совместимость (безопасность данных): Поскольку старые поды полностью уничтожены 
   до появления новых, в кластере в любой момент времени существует только одна версия 
   приложения. Это гарантирует, что миграции БД (если они есть) не сломаются из-за 
   запросов от старой версии, и пользователи не получат ошибок из-за несовместимости 
   API во время переключения трафика.

   - Простота: Это нативная стратегия Kubernetes, не требующая дополнительных 
   инструментов (Ingress-контроллеров для Canary или внешних контроллеров для Blue-Green), 
   что снижает риск ошибок при настройке.

Единственный минус стратегии Recreate — это Downtime (простой). Приложение будет недоступно 
на время, пока старые поды завершаются, а новые запускаются. Однако, учитывая жесткие 
ограничения по ресурсам и критическую несовместимость версий, этот простой является вынужденным 
и оправданным компромиссом. Мы можем минимизировать его, настроив terminationGracePeriodSeconds 
и readinessProbe для быстрого старта новых подов.

### Итог

Выбираем Recreate, так как это единственный способ гарантировать успешное обновление 
без превышения лимитов ресурсов и без ошибок обработки запросов из-за смешивания версий, 
ценой небольшого запланированного простоя.

Для минимального времени обновления используем стратегию RollingUpdate с настройками:
   - maxSurge: 1 - создаем 1 новый под до удаления старого

   - maxUnavailable: 0 - гарантируем, что всегда будет доступно минимум 5 подов

Обновляем образ:
```bash
kubectl set image deployment/nginx-multitool nginx=nginx:1.20
```
И следим за процессом обновления:
```bash
kubectl rollout status deployment/nginx-multitool
```

### Откат после неудачного обновления:

```bash
kubectl rollout undo deployment/nginx-multitool
```
Следим за откатом:
```bash
kubectl rollout status deployment/nginx-multitool
```
Проверяем, что все поды вернулись к версии 1.20:
```bash
kubectl get pods -l app=nginx-multitool
kubectl exec -it deployment/nginx-multitool -c nginx -- nginx -v
```
