## Задание. Необходимо определить требуемые ресурсы

Известно, что проекту нужны база данных, система кеширования, а само приложение состоит из бекенда и фронтенда. Опишите, какие ресурсы нужны, если известно:

    1.Необходимо упаковать приложение в чарт для деплоя в разные окружения.
    2.База данных должна быть отказоустойчивой. Потребляет 4 ГБ ОЗУ в работе, 1 ядро. 3 копии.
    3.Кеш должен быть отказоустойчивый. Потребляет 4 ГБ ОЗУ в работе, 1 ядро. 3 копии.
    4.Фронтенд обрабатывает внешние запросы быстро, отдавая статику. Потребляет не более 50 МБ ОЗУ на каждый экземпляр, 0.2 ядра. 5 копий.
    5.Бекенд потребляет 600 МБ ОЗУ и по 1 ядру на копию. 10 копий.

---
## Цель задания

Рассчитать требования к кластеру под проект.

## Исходные данные

| Компонент | Ресурсы на копию | Кол-во копий |
| --- | --- | --- |
| База данных | 4 ГБ ОЗУ, 1 CPU | 3   |
| Кеш | 4 ГБ ОЗУ, 1 CPU | 3   |
| Фронтенд | 50 МБ ОЗУ, 0.2 CPU | 5   |
| Бекенд | 600 МБ ОЗУ, 1 CPU | 10  |

* * *

## 1\. Расчёт ресурсов приложения

### Память (RAM)

-   БД: `4 ГБ × 3 = 12 ГБ`
-   Кеш: `4 ГБ × 3 = 12 ГБ`
-   Фронтенд: `0.05 ГБ × 5 = 0.25 ГБ`
-   Бекенд: `0.6 ГБ × 10 = 6 ГБ`

**Итого по памяти:** `12 + 12 + 0.25 + 6 = 30.25 ГБ`

* * *

### CPU

-   БД: `1 × 3 = 3 CPU`
-   Кеш: `1 × 3 = 3 CPU`
-   Фронтенд: `0.2 × 5 = 1 CPU`
-   Бекенд: `1 × 10 = 10 CPU`

**Итого по CPU:** `3 + 3 + 1 + 10 = 17 CPU`

* * *

## 2\. Учёт служебных ресурсов Kubernetes и системных компонентов

На каждой ноде Kubernetes резервирует часть ресурсов под:

-   kubelet
-   container runtime
-   kube-proxy
-   системные демоны (sshd, systemd и т.п.)
-   операционную систему

Рекомендуется закладывать **~20–25% ресурсов ноды** на служебные нужды.  
Также нужно учитывать ресурсы на **мониторинг, логирование, ingress-controller** и другие кластерные сервисы.

Для простоты заложим **+25% к ресурсам приложения**.

### С учётом служебных ресурсов:

-   Память: `30.25 × 1.25 ≈ 37.8 ГБ` → округлим до **38 ГБ**
-   CPU: `17 × 1.25 ≈ 21.25 CPU` → округлим до **22 CPU**

* * *

## 3\. Расчёт количества нод

Планируем использовать **однотипные ноды** для простоты эксплуатации.

Возьмём ноду с характеристиками:

-   **8 CPU**
-   **16 ГБ RAM**

### Сколько нужно нод по CPU?

`22 / 8 = 2.75` → минимум **3 ноды**

### Сколько нужно нод по памяти?

`38 / 16 = 2.375` → минимум **3 ноды**

Итого по ресурсам — **3 рабочие ноды**.

* * *

## 4\. Запас на отказ одной ноды

Чтобы кластер продолжал работать при потере одной ноды, нужно добавить ещё **одну ноду**.

**Итого: 4 рабочие ноды.**

* * *

## 5\. Итоговая конфигурация кластера

### Рабочие ноды

| Параметр | Значение |
| --- | --- |
| Количество | 4   |
| CPU на ноду | 8 vCPU |
| RAM на ноду | 16 ГБ |
| Диск | 100 ГБ SSD |
| Итого CPU | 32 vCPU |
| Итого RAM | 64 ГБ |

* * *

## 6\. Дополнительно (рекомендации)

-   Для **БД и Кеша** использовать **StatefulSet** с PVC.
-   Для отказоустойчивости БД и Кеша настроить **анти-аффинити**, чтобы поды не размещались на одной ноде.
-   Фронтенд можно вынести за Ingress и масштабировать отдельно.
-   В production стоит выделить **отдельные ноды** под служебные сервисы (Ingress, мониторинг, логирование), но для текущего расчёта они учтены в запасе.

* * *

## Итоговый ответ

**Кластер:**

-   4 рабочие ноды
-   Каждая: 8 vCPU, 16 ГБ RAM, 100 ГБ SSD
-   Суммарно: 32 vCPU, 64 ГБ RAM
-   Запас позволяет пережить отказ одной ноды без деградации сервиса.
